## The finding that changes how I write validation everywhere

**`assert` is deleted by `NDEBUG`, and CMake's Release config is `-O3 -DNDEBUG`.** So asserts do not
exist in the build that produces every benchmark number. Verified:

```
Debug   (-O0):           Assertion `config.rate_x + config.rate_y <= 0.5' failed.  exit=134
Release (-O3 -DNDEBUG):  rx+ry=1.0000  -> UNSTABLE, and we got here.               exit=0
```

The rule I now use:

- **`assert`** = "this cannot happen unless *my own code* is buggy" — internal invariants, fine to
  remove in Release.
- **A check that throws** = "the caller or user could get this wrong" — must survive Release.

`rx + ry <= 1/2` is the one guarantee protecting every number in the report. It costs one comparison
*per run*. It is not an assert.

## Two validation traps, both measured

**1. Validate the INPUTS, not the derived values.** `assert(delta_x > 0)` does **not** catch
`n_interval_x = 0`, because floating-point `1.0/0` is `inf` and `inf > 0` is true. Worse, the whole
config then *looks healthy*: `dx=inf` but `rx+ry=0.4`, because `1/inf^2 = 0` so the x-direction
silently contributes nothing and `ry` alone makes up the 0.4.

**2. An upper bound says nothing about sign.** `require(rx + ry <= 0.5)` passed for
`stability_coeff = -1.0`, which gives `rx+ry = -0.5` and **`dt = -2.5e-05`** — time running
backwards. Same lesson from the other direction: check the input, or make the bound two-sided.

## C++ ownership — why `unique_ptr<real[]>`, not raw `new[]`

| | |
|---|---|
| raw `new[]` + destructor, copy not handled | **`free(): double free detected`, abort at runtime** |
| `unique_ptr` | **`error: use of deleted function`** — refuses to compile |

Same mistake, caught at completely different times. `unique_ptr` turns my own C-era rule
("DO NOT COPY ARRAYS", which I had to *remember*) into something the compiler enforces.

Two surprises inside that:

- **`std::make_unique<T[]>(n)` value-initialises**; `std::unique_ptr<T[]>(new T[n])` does not.
  128 MB: 0.0781 s vs **0.0330 s**. The speed is minor (once per run) — the real reason is
  **first-touch**: value-init is a *serial* memset, which on a NUMA machine places every page near
  whichever thread ran the constructor. The grid should be touched first by a parallel loop.
- **Writing an empty `~Field() {}` silently deletes the implicit move constructor**, making the type
  non-swappable — `std::swap` then fails to compile. Verified with `is_move_constructible`. Since
  `unique_ptr` already cleans up, write no destructor at all.

## Build system

- **ninja**, but not for speed: measured ~15% (0.518 s vs 0.601 s full build) — irrelevant at this
  size. The real reason is that **ninja parallelises by default and `make` does not**; a bare `make`
  is serial and you have to remember `-j` every time.
- **Empty `CMAKE_BUILD_TYPE` means `-O0`**, silently, with no warning. Fatal for a benchmarking
  project. `CMakeLists.txt` now forces Release.
- **Correction to my own note:** omitting `-fopenmp` from the *link* line does **not** fail
  silently — it fails loudly with ``undefined reference to `__offload_func_table'``. Fixed in
  `CLAUDE.md`.

## Measurement lessons (Claude's errors, kept deliberately)

- **Static instruction count is not speed.** The accessor with asserts live compiled to 90
  instructions; with `-DNDEBUG`, **151** — because removing the asserts let the compiler vectorise.
  Timing showed all variants equal. Count instructions and you would conclude the opposite of the truth.
- **Dead-code elimination struck twice more** (an allocation benchmark reporting 0.0000 s; earlier a
  latency sweep printing all zeros). Running total for the week: **six** silent benchmark failures,
  none of which errored. Every one was caught by a number being implausible.
- One benchmark I wrote to exercise `dx != dy` accidentally used square cells, so it did not test
  what I claimed. **A test passing does not mean it tested what you think.**
