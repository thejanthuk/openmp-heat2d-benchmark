## Findings on `exact()`

- **`int x, int y, int t` made it return 0 for every input** — `0.5` truncates to `0`. **GCC gave zero
  warnings under `-Wall -Wextra -Wpedantic`**; Clang flagged it (`-Wliteral-conversion`). GCC's
  `-Wfloat-conversion` catches it and is silent on all existing code, so it was recommended for the
  CMake warning line. It also guards a future `real = float` switch.
- It used the unit-square formula, ignoring `length_x`/`length_y` — the same bug fixed in the
  initial condition a day earlier, now in the file the convergence test will check against. The decay
  rate needs the lengths too: `exp(-alpha pi^2 (1/Lx^2 + 1/Ly^2) t)`.
- `constexpr` with `std::sin`/`std::exp` cannot be honoured in C++17 (they are not `constexpr`); it
  compiled only because nothing evaluated it at compile time. Replace with `inline` — not just delete,
  since `constexpr` was what made it implicitly inline in a header.
- `Config` by value would copy ~112 bytes per grid point inside `l2_error`; use `const Config&`.

## The measurement worth keeping: an unscaled norm fakes first-order convergence

Same correct solver, same error field, four reductions (N = 20..160, fixed t_end):

| Norm | Observed order |
|---|---|
| `sqrt(sum e^2)` — unscaled | **1.005, 1.001, 1.000** |
| `sqrt(sum e^2 * dx*dy)` — scaled L2 | 2.005, 2.001, 2.000 |
| `sqrt(mean e^2)` — RMS | 2.042, 2.020, 2.009 |
| `max |e|` — L-infinity | 2.005, 2.001, 2.000 |

In 2-D, ~n^2 points each with error ~h^2 give sqrt(n^2 h^4) = n h^2 = h: one order lost. The `dx*dy`
factor is the area each point represents, turning the sum into an approximation of the integral.

**Order 1 now has two unrelated causes** — a wrong `dx` (per an earlier guide's failure table) *or* an
unscaled norm. If a convergence study shows order 1, check the norm before suspecting the solver.

Recommended: `l2_error(const real* u, real t, const Config&)` over interior points, accumulated in
`double`, returning `sqrt(sum * dx * dy)`; plus a `max_error` (L-infinity) as a cross-check.

## Later: revised `exact.hpp`; `l2_error` and `max_error` reviewed by running them

`exact()` is now correct — centre 0.820869 on both the unit square and a 1x0.5 domain, zero warnings
with `-Wfloat-conversion` (now in `CMakeLists.txt`). Include paths still lack the `heat/` prefix.

Both error functions were checked on a real solved field rather than by reading:

- **`l2_error` returned `-nan`** — it summed raw differences instead of their squares. All 9801
  interior errors are negative (the explicit scheme decays slightly faster than the exact solution),
  so the sum was negative and `sqrt` gave NaN. With mixed-sign errors the same bug would instead
  cancel to a *tiny*, excellent-looking number.
- **`max_error` returned `-1.8661e-05`** — correct magnitude, wrong sign — from two bugs that cancel
  only because every error is negative: the comparison was backwards (keeping the minimum) and there
  was no `abs`. On a problem with positive errors it would return 0.0.
- Correct max error, 1.8661e-05, matches the old C implementation's `max_diff = 1.866e-05`.

**Why the C version needed no lengths:** it hard-coded `l_x = l_y = 1.00`, where the general formula
reduces exactly to `sin(pi x) sin(pi y) exp(-2 alpha pi^2 t)`. Every test used L = 1, the one value
where the lengths cancel, so no test could distinguish the special case from the general one.

## Later: `test_exact.cpp` skeleton — and a NaN-blind check caught by testing the test

Krit asked how `test_exact` gets the heat array from `main.cpp`. It doesn't: a known-answer test
**builds its own field** (`exact + 1e-3`) and never runs the solver, so only the error functions can
be wrong. (`test_convergence` is different — it tests the solver, which is why it needs ADR-004's
`run()`.)

Before handing over the skeleton, Claude ran it against the three bugs Krit had just fixed,
reintroduced one at a time. It caught all three — but the missing-square bug produced only 4 of the
expected 6 failures. The all-negative case made `l2_error` return NaN, and the check
`if (abs(got - want) > tol)` **passed**, because every comparison with NaN is false. Rewritten as
`if (!(abs(got - want) <= tol))` it fails on NaN, and the bug produces all 6 failures.

**Rule: a check must pass only when closeness is proven — `!(diff <= tol)` — never fail only when
distance is proven — `diff > tol`.** Only the first catches NaN. Same trap as the stability `assert`
a week earlier.

## Later: the convergence test — right numbers, inverted verdict

Krit fixed the CMake ordering error (`target_include_directories` on a target not yet created → configure
failed; moved to `heat_common INTERFACE src`) and wrote `tests/convergence.cpp` with `config_at_time`
(probe `make_config` for dt, `ceil` the step count, rescale `coeff` so `steps * dt == t_end`).

The computed errors matched the targets exactly on both domains (square; Ly=0.5 with nx = 2 ny), with
orders -> 1.9987 and 1.9991. **The pass/fail logic was inverted**: a correct solver scored 2 failures
and a stale-buffer solver 1. Causes: `!std::abs(x) <= tol` (precedence — GCC `-Wlogical-not-parentheses`
flags it), `if (prev < 1e-5) fail++` (backwards), and a copy-pasted second loop that lost its checks.

The stale-buffer solver's order was **1.9996 — closer to 2 than the correct solver's 1.9987** — a live
demonstration that only the magnitude check (5.6e-05 vs 4.3e-06) can catch it.

Recommended: one `check_convergence(name, x_multiplier, length_y)` called twice, so the checks cannot
drift apart; NaN-proof checks; order printed only from the second grid. Verified in a copy: correct
solver -> exit 0; stale buffer -> exit 2, both failures naming the magnitude check.

**Lesson: a test must pass on correct code AND fail on broken code. Checking the printed numbers is
not checking the test — check the exit code, against a known-good and a known-bad version.**

## Later: CPU OpenMP variant — and two corrections to Claude's own tooling advice

Krit built `src/openmp_cpu/` as a copy of the serial variant: the solver diff is exactly the namespace
and two `parallel for collapse(2)` pragmas (update loop, plus the initial condition for first touch —
his reasoning: the extra pragma is part of the parallelisation being measured, and first touch changes
the *timed* kernel's speed on multi-socket machines). Output **byte-identical to serial in 20/20 runs**
(5 configurations incl. 1000x1000, at 1/2/4/8 threads), confirming his prediction. Refinement: the
machine code differs (serial vectorised, 14 ymm ops; `collapse(2)` almost all scalar, 2) — the compiler
fixes each point's arithmetic, including FMA fusion, before choosing vector width.

**Correction 1 — TSan.** It reported 20 races on the correct solver. A trivially correct program was
flagged by both GCC and Clang TSan: the OpenMP runtimes synchronise thread pools invisibly to TSan. The
2026-09-15 claim "GCC TSan is clean on correct OpenMP" was wrong (one `reduction` test, whose atomics
TSan can see). Post-mortem: `docs/postmortems/2026-09-22-tsan-openmp-false-positives.md`. The race
check for OpenMP here is differential testing against serial across thread counts.

**Correction 2 — clang-tidy.** Krit removed `<initializer_list>` and `heat/exact.hpp` from
`tests/convergence.cpp` because the cheat-sheet's clang-tidy loop flagged them. The loop lacked `-Isrc`
and filtered out `error:` lines, hiding a `file not found` that made its findings guesses. He followed
the tool correctly; the tool was misconfigured. Now `clang-tidy -p build` reads the build's own
`compile_commands.json`, so its flags cannot drift. Both includes restored.

**Pattern across both corrections: Claude's tooling advice was stated more confidently than its
evidence supported.** In each case the tell was a contradiction with something stronger —
bit-identical results; a `file not found` error.

## Later: first timing — Krit's prediction was wrong, and so was his first explanation

ADR-005 implemented (`result.hpp`, `timer.hpp`; loop timed inside `run()`), now *current*. N=2000, 100
steps, best of 5: serial 1.018 s; OpenMP 0.72x at 1 thread, never better than 0.96x at 2/4/8/16 threads.
Prediction was (a) 1.0x, (b) 4x.

Krit's explanation was "thread overhead". Two tests falsified it:
1. An empty parallel region costs 0.74 us (1 thread) to 7 us (8 threads): at most 0.7 ms over 100 steps
   against a ~400 ms gap.
2. Same threads **without** `collapse(2)`: 1 thread goes from 0.76x to 1.05x. The cause is `collapse(2)`
   blocking vectorisation (14 -> 2 vector ops, measured earlier) — evidence Krit already had.

Part (b): serial already runs at 9.17 GB/s against a measured 9.27 GB/s ceiling — 99% of the single
memory channel — so no thread count can help. The scalar `collapse(2)` kernel cannot saturate memory from
one core but can from four, which is why its penalty vanishes at 4 threads.

**Lesson: an explanation is a hypothesis. Test it with an experiment where it predicts something
different from the alternatives** — here, "remove the overhead" versus "remove `collapse(2)`".

Remaining tidy-ups: the two solvers now differ in a third place (`const auto` vs `const double` for
`seconds`); `timer.hpp` puts `Clock`/`seconds_since` in the global namespace. The 8-thread result
(0.69x, worse than 16) should be re-run before being explained.

## Later: Krit challenged "collapse(2) blocks vectorisation" — it held

Krit did not believe the claim (and first read it as being about compile time — it was not). Checked
properly: compile time identical (0.21 s); **GCC's own `-fopt-info-vec` report** shows the kernel loop
vectorised with 32-byte vectors without `collapse(2)`, and not vectorised with it (C: "unsupported control
flow"; C++: "not profitable"); his original C code runs 1.28x slower at 1 thread with `collapse(2)`; and
his own earlier benchmark had already shown 0.55-0.68x. Claude's earlier "14 vs 2 vector ops" was a crude
whole-file count — the compiler report is the right evidence. An empty grep of the report was nearly
misread as "nothing reported" until the window was widened: the collapsed loop is attributed to the
pragma's line. Side finding: aliasing-versioned loops — the concrete case for `restrict` (gate Q4).
