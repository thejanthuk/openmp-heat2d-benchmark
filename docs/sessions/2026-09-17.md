## The two results worth remembering

**1. Loop order costs up to 8.1x, and the cache levels fail *together*.** Same array, same work,
only the loop order swapped: 1.3x penalty at N=256 (fits cache) rising to **8.1x at N=4096** —
converging on the 8-doubles-per-64-byte-line prediction. The non-obvious part: L2 and L3 do not help,
because every level uses the same 64-byte line *and* every level indexes by a power-of-two number of
sets. At N=2048 a row is exactly 256 lines, so **L1 reaches 1 set (1.6% usable), L2 4 sets (0.4%),
L3 32 sets (0.4%)**. Reuse needs 2048 lines resident; L3 offers 384.

Proof: adding **one element per row** (8 bytes) made column traversal **1.4-1.9x faster** at
N=1024/2048/4096. Nothing about capacity or traffic changed — only the set mapping. That is a
**conflict** miss, distinct from capacity and compulsory misses.

This does **not** contradict the "padding does not help" note: the stencil runs stride-1 with ~4
streams into an 8-way cache and nothing collides. Different regime, both results correct.

**2. Solver iteration counts, measured.** `-laplacian(u)=1`, tol 1e-8:

| N | Jacobi | RB-GS | SOR(opt) | CG |
|---|---|---|---|---|
| 128 | 60481 | 30816 | 528 | **237** |
| *scaling* | O(N^2) | O(N^2) | O(N) | O(N) |

**255x between Jacobi and CG at N=128**, widening with N.

## Two benchmark-design mistakes I should learn from (Claude made both)

- The first latency sweep printed **all zeros** — the compiler deleted the loop (no volatile sink).
  The second **mislabelled every working set by 8x** — one pointer per 64-byte line, but pointers are
  8 bytes. Both are documented traps in my own lab notes, walked into anyway. The tell was
  implausible numbers (0 ns; L2 as fast as L1), never an error message.
- The first solver benchmark used `sin(pi x)sin(pi y)` as the RHS — an **eigenvector** of the discrete
  Laplacian — so **CG converged in 1 iteration** and looked miraculous. A test problem can be too
  easy in a way that resembles a triumph.

**Pattern: a benchmark fails silently far more often than it errors. The defence is a prediction to
compare against.** Which is the argument for Step 1.
