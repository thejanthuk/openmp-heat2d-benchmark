## Measured ceilings

| Ceiling | Measured | Theoretical | Achieved |
|---|---|---|---|
| Host memory (triad, 32 MB arrays) | 9.27 GB/s | 19.2 | 48% |
| PCIe host->device / device->host | 3.66 / 3.73 GB/s | 15.75 | 23% |
| **GPU triad, resident, best geometry** | **7.15 GB/s** | **112** | **6.4%** |

Host bandwidth is flat across 1/2/4/8 threads — one core saturates the single channel, as expected.

## The 25x: root cause

**GCC's nvptx OpenMP runtime caps threads per team at 20 and defaults to 8.** Default launch is
`num_teams=10 x 8 = 80 threads` on a GPU with 640 cores and ~10,240 thread slots — under 1%
occupancy. Tested and **all ignored**: `thread_limit`, explicit `parallel num_threads()`,
`OMP_NUM_THREADS`, `OMP_TEAMS_THREAD_LIMIT`, `OMP_THREAD_LIMIT`.

How it was found quickly: **a ten-line triad reproduced the anomaly with the solver removed** — no
stencil, no `collapse(2)`, no indexing. That eliminated three of seven hypotheses in one run. Then
querying `omp_get_num_teams()`/`omp_get_num_threads()` from inside the kernel gave the answer directly.

**My original result was right; my original explanation was wrong.** "GPU offload is slower than one
CPU core" is true *of this toolchain*. It is not a statement about GPUs, my stencil, `collapse(2)`,
or FP64. The correct claim — that GCC's offload reaches 6% of device bandwidth — is a stronger and
more interesting result.

**Caveat I must keep saying: "GCC's offload", not "OpenMP offload".** Clang and NVHPC use different
runtimes. Untestable here (`libomptarget` absent), and now logged as the project's best candidate
research question.

**The naive-vs-optimized comparison survives intact** — both versions share the cap, so their
difference is still a clean PCIe measurement, and it matched its model to 1%.

## Method note worth keeping

Three benchmarks this session first produced impossible numbers — host bandwidth of **103,562 GB/s**
against a 19.2 GB/s ceiling, because the compiler deleted the loop. Earlier the same day: a latency
sweep printing all zeros, working sets mislabelled 8x, and a solver benchmark whose RHS was an
eigenvector so CG "converged" in one iteration.

**None of them errored.** Every one was caught by a number being implausible against something
expected. That is the entire case for having a ceiling before having a result.
