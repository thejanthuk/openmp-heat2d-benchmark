## Results — everything works, no kernel change needed

| Tool | Version | Verified by |
|---|---|---|
| GDB | 17.2 | backtrace with source lines and arg values on a real SIGSEGV; `info threads` shows the OpenMP team (main + 3 libgomp workers) |
| rr | 5.9.0 | record, deterministic replay of the same SIGSEGV, and **reverse execution** — `reverse-continue` walked back to `i=64` then `i=63` |
| perf | 7.2 | `perf stat` with `cycles:u`, `L1-dcache-load-misses:u`, `LLC-load-misses:u`, `dTLB-load-misses:u`; `perf record`/`report` on a process |
| Valgrind | 3.27.1 | installed |
| ParaView | — | not yet present |

**The kernel change I was expecting is not needed.** `kernel.perf_event_paranoid=2` already permits
per-process user-space counters, which is all that rr and this project's profiling require. rr is
not setuid and holds no capabilities — paranoid=2 is simply sufficient. Only two things are blocked,
and I need neither: kernel-space events (`cycles:k`) and system-wide `perf record -a`. If I ever
want those it's `sudo sysctl kernel.perf_event_paranoid=1` — a sysctl, not a rebuild.

Worth knowing: `perf` silently appends `:u` to event names. That *is* the restriction being applied,
and for profiling a compute kernel it is what I want anyway.

## Two things measured that changed how I should use these

**rr serialises threads onto one core** to get determinism — measured 9.4x slowdown on the 4-thread
reduction. So rr **cannot find races and cannot time parallel code**. Clean division:
TSan finds races · rr debugs logic · perf measures speed · ASan finds memory errors ·
`git bisect` finds regressions.

**ASan vs gdb, demonstrated on one program** that writes one element past a `malloc`ed grid from
`i=64`:

| Build | Outcome |
|---|---|
| plain `gcc -Og` | printed `survived` — **no crash**, the write landed in heap slack |
| `-fsanitize=address` | caught at **`i=64`**, first offending write, with allocation site |
| gdb on the plain build | crashed only at **`i=323`** — 259 iterations late |

The plain build is the dangerous one: a genuine out-of-bounds write that silently corrupts heap
slack. That is the argument for `-fsanitize=address,undefined` living in every debug build, not
being reached for after something crashes.
