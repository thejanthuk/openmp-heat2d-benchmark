## The finding that set the agenda

My reported result — "GPU offload is ~3x slower than a single CPU core" — is a toolchain artifact,
not physics. At N=2000 / 500 steps the kernel moves ~48 GB:

| Version | Measured | Roofline | |
|---|---|---|---|
| Serial CPU | 3.97 s | 4.0 s (48 GB / 11.9 GB/s) | at ~100% of achievable bandwidth |
| CPU OpenMP, best | 3.56 s | ~4.0 s, same ceiling | bandwidth-bound as expected |
| naive − optimized | 12.64 s | 12.8 s (64 GB / ~5 GB/s PCIe) | transfer model good to 1% |
| GPU optimized | 13.15 s | **0.53 s** (48 GB / ~90 GB/s) | **25x off** |

Because the transfer half matches its model, my `target data` reference-counting analysis stands.
Only the kernel is broken. Two smaller defects found in the same data: `collapse(2)` costs ~1.6x on
the CPU (`cpu-1t` is 0.55–0.68x of serial everywhere), and everything was built `-O2` without
`-march=native`, so it generated SSE2 on an AVX2 machine.

## Added: correctness tooling (TSan + debugger)

I flagged that sanitizers and debugger technique were missing from the plan — especially *when* to
reach for each. Now `docs/debugging-toolkit.md`, built from measurements on this machine rather than
internet advice, and folded into the plan at Week 3 (TSan before the first threaded timing run) and
Week 10 (tasks make races easy to write).

Findings worth remembering:

- **GCC is the right TSan for OpenMP here, not Clang** — the reverse of the usual "Clang + Archer"
  advice. Archer isn't installed, so Clang's `libomp` reports a false positive on *correct* code;
  GCC is clean and still catches real races.
- **Reading a report is one question:** does any frame name a file I wrote? True positive top frame
  is `main._omp_fn.0 myfile.c:11`; false positives are all `libomp.so`/`libgomp.so`/`libc`.
- **Costs:** ASan+UBSan ~5x (leave on always), TSan ~71x (N=64 only), and they cannot be combined —
  the compiler refuses.
- **The trap:** a reduction changing run-to-run is usually *not* a race. Verified — `schedule(static)`
  at fixed threads is bit-identical over 5 runs; `schedule(dynamic)` gives 5 different values;
  1/2/4/8 threads give 4 different values even under static. My L2 error is a reduction, so version
  comparisons need a tolerance, never `==`.
- **`gdb` is not installed.** Neither is `rr`. Added to the emerge list.
- **Nothing reaches the GPU** — no sanitizer, no debugger. GPU correctness is differential against
  the serial oracle plus the two device assertions.

Worth doing deliberately in Week 3: write the in-place update bug on purpose and see it through two
lenses — TSan names the line, and the convergence order collapses from 2 to 0. Same bug, two
signatures. That also answers gate question 1 by demonstration.
